3. CORE GAME CONCEPT
==================================================

Working title:
WIND EFFIGY
(name may change later)

Core fantasy:

BORROW THE WORLD TO MOVE THROUGH THE WORLD.

The player controls a small ritual Wind Puppet living in an old mountain village.

The protagonist is not a powerful hero.

It does not simply fly.

It does not receive a large set of abilities.

Instead, it moves by borrowing force from the environment.

The village itself becomes the movement system.

The player sees:
- roof beams
- branches
- bamboo
- hanging structures
- balconies
- bells
- bridges
- architectural gaps

and thinks:

“Can I use that to get there?”

The core emotional/gameplay fantasy is:

The player begins by moving THROUGH the village.

As skill develops, the player begins moving WITH the village.

Architecture changes from scenery into possibility.

==================================================
4. CORE PLAYER EXPERIENCE
==================================================

The desired experience is:

EASY TO UNDERSTAND

SATISFYING IMMEDIATELY

HARD TO MASTER

The player should understand the core interaction within seconds.

But several minutes later, a better player should be able to traverse the SAME space much more elegantly and quickly.

The game should generate thoughts like:

“I think I released too early.”

“I could probably reach that roof.”

“What if I enter the swing with more speed?”

“Can I connect those two anchors without touching the ground?”

“There might be a faster route.”

“I almost had that. I want to try again.”

If the player does not naturally think these things, the core mechanic needs more iteration.

6. CORE MECHANIC DIRECTION
==================================================

The current strongest mechanic concept is:

WIND THREAD.

The Wind Puppet has a physical thread / cord / ribbon that can temporarily attach to parts of the environment.

The fundamental movement loop is:

SEE POSSIBILITY
→ ATTACH
→ SWING
→ BUILD / REDIRECT MOMENTUM
→ RELEASE
→ TRAVEL
→ LAND OR CHAIN
→ SEE NEXT POSSIBILITY

The mechanic should NOT behave like:

“press button and automatically grapple toward target.”

Instead it should feel like:

“attach to the world and use physics/timing to redirect yourself.”

==================================================
7. WIND THREAD — MECHANICAL REQUIREMENTS
==================================================

ATTACH:

- fast and responsive
- target must be readable
- forgiving enough for beginners
- not fully automatic
- player should understand what they attached to

SWING:

- gravity matters
- entry velocity matters
- tether position matters
- player timing matters
- momentum should remain understandable
- player accelerates through natural parts of the arc
- limited directional influence is allowed
- player input should shape the trajectory, not replace physics

RELEASE:

This is the main skill expression.

Release timing should determine:
- height
- distance
- direction
- ability to connect to next object

Do NOT assign an arbitrary preset launch direction.

The player should feel:

“I created that trajectory.”

CHAINING:

Allow:

swing
→ release
→ airborne travel
→ attach another anchor
→ swing again

The best moments should involve continuous movement without unnecessary stopping.

==================================================
8. CORE DESIGN PRINCIPLE:
ONE MECHANIC, MANY POSSIBILITIES
==================================================

Do NOT create many unrelated abilities.

Use a SMALL NUMBER of consistent rules interacting with different environmental properties.

Prefer:

ONE VERB
×
DIFFERENT MATERIAL BEHAVIOR
×
GEOMETRY
×
TIMING

over:

TEN DIFFERENT BUTTONS.

Example interaction categories:

-----------------------------------
RIGID STRUCTURE
-----------------------------------

Examples:
- roof beam
- stone support
- tree branch

Behavior:
- stable anchor
- predictable movement
- ideal for learning

-----------------------------------
ELASTIC STRUCTURE
-----------------------------------

Example:
bamboo

Behavior concept:
- bends under force
- stores energy
- returns some energy
- stronger approach can produce stronger launch

Do NOT implement this as:
fixed bounce animation + fixed launch velocity.

Prefer a shared physical/property-based model.

-----------------------------------
RESONANT STRUCTURE
-----------------------------------

Examples:
- temple bell
- wind chime

Behavior:
- reacts to motion / impact / tension
- motion produces sound
- stronger interaction produces stronger resonance

This may later affect nearby environment.

Example:

player transfers momentum
→ bell moves
→ resonance strength increases
→ nearby hanging objects move
→ birds react

Do NOT hardcode this entire chain as a cinematic event if a reusable event/property system can express it simply.

-----------------------------------
OPTIONAL SURFACE INTERACTION
-----------------------------------

Example:
water

If and ONLY IF the core mechanic is already fun:

high-speed movement may allow a short skim or momentum-preserving interaction.

Do not add this simply for feature count.

==================================================
9. SYSTEMIC / EMERGENT DESIGN PRINCIPLE
==================================================

Take inspiration from systemic design and emergent interaction.

The goal is NOT to reproduce Dwarf Fortress-scale simulation.

The goal is to borrow this idea:

SMALL CONSISTENT RULES
+
DIFFERENT OBJECT PROPERTIES
=
MULTIPLE UNDERSTANDABLE RESULTS

Prefer:

PROPERTY + RULE + INTERACTION

over:

SCRIPTED SPECIAL CASE.

Example:

BAD:
“When player touches bamboo, play bounce animation and launch player.”

BETTER:
“Bamboo has elasticity.
Applied force affects bend.
Stored energy influences return.”

BAD:
“When player hits bell, play bird animation.”

BETTER:
“Bell produces resonance intensity.
Responsive entities can react to resonance.”

The system should remain SMALL and readable.

==================================================
11. PLAYER SKILL CURVE
==================================================

The same mechanic should serve different skill levels.

BEGINNER:

“I know what to press and I can move forward.”

INTERMEDIATE:

“I understand release timing and trajectory.”

ADVANCED:

“I can preserve speed, chain anchors, discover shortcuts, and traverse the same level much faster.”

Expertise should be visible in movement.

A beginner and a skilled player should NOT move through the exact same section in the exact same way.

==================================================
12. CORE LOOP
==================================================

Moment-to-moment gameplay should approximately follow:

SEE

→ choose a possibility

COMMIT

→ attach / jump / enter motion

EXECUTE

→ timing / steering

FEEDBACK

→ immediate audiovisual and physical response

RESULT

→ new trajectory / new location

DISCOVER

→ next movement opportunity

The player should rarely spend long periods simply walking.

Every few seconds there should ideally be:

- a movement decision
- an anchor
- a route possibility
- a timing challenge
- an environmental response
- a shortcut possibility
- a visual landmark

==================================================
13. FAILURE DESIGN
==================================================

Failure should make the player want another attempt.

Prefer:

- lower recovery platforms
- forgiving landing zones
- quick retries
- partial progress loss
- understandable causes

Avoid:

- long reloads
- constant instant death
- replaying boring sections
- unclear physics outcomes

Desired reaction:

“I almost got it.”

NOT:

“I don't want to do that again.”

MANDATORY GAMEPLAY GATE
==================================================

DO NOT build the full level or begin the final art pass immediately after the mechanic technically works.

Before significant content production, create a small 30–60 second GREYBOX PLAYGROUND whose only purpose is to evaluate whether the core mechanic is actually enjoyable.

It should include:

- one very easy use of the mechanic
- one timing-sensitive use
- one two-anchor chain
- one failed-action recovery area
- one optional shortcut
- enough open space to experiment

Create approximately THREE tuning variants of the SAME core mechanic.

Do NOT create three completely different games.

For example:

A — heavier and more controlled
B — faster and more responsive
C — stronger momentum and wider swing arcs

Expose important tuning values clearly so they can be changed quickly.

Then STOP major production work.

Do not proceed to full level production merely because the mechanic functions.

The prototype must first be evaluated by a HUMAN PLAYER.

The human playtest should answer:

1. Does the player feel responsible for the resulting trajectory?

2. When the player fails, do they understand why?

3. Does better timing visibly produce better results?

4. After several attempts, does the player noticeably improve?

5. Does the player begin imagining their own routes?

6. Does the player voluntarily repeat the mechanic even without rewards?

7. Does failure produce:
   "I almost had it, let me try again"
   rather than frustration or confusion?

Only after human feedback confirms that the core interaction has potential should development proceed to the full vertical slice.

Automated tests may verify:
- reachability
- physics stability
- impossible jumps
- parameter ranges

But automated tests MUST NOT be treated as proof that the mechanic is fun.

FUN REQUIRES HUMAN PLAYTESTING.
